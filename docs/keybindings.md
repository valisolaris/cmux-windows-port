# cmux-tui 既定キーバインド111

出典(コードから読み取った実物のみ。推測なし):

- `cmux/cmux-tui/crates/cmux-tui/src/config.rs` の `Keys::default()`(prefix と全アクションの既定チャード)
- `cmux/cmux-tui/crates/cmux-tui/src/sidebar_files/mod.rs` の `handle_key()`(ファイルサイドバー内のキー)
- `cmux/cmux-tui/crates/cmux-tui/src/app.rs` の `hit_at()`/`handle_left_up()`/`handle_scroll()`(ファイルサイドバーのマウス操作)

対象コミット: windows-port ブランチ(main = 7652d3b からの一点改造)。既定は tmux 準拠。

## 押し方の基本(重要)

- **prefix = `Ctrl+B`**。非 Alt 系のキーは、まず `Ctrl+B` を押して離し、続けて対象キーを押す(tmux と同じ 2 段階)。
- **Alt 系はモードレス**: `Alt+<キー>` は prefix なしでそのまま効く(`config.rs` の `modeless_action_for`: Alt 修飾のチャードのみモードレス)。
- 大文字表記(例 `X`, `B`, `W`, `S`)は Shift 併用を意味する(`Ctrl+B` のあと `Shift+x` 等)。
- 設定 `%APPDATA%\cmux\cmux-tui.json` の `keys` で上書き可能。`alt_shortcuts: false` で Alt 系モードレスを一括無効化できる。
- **IME(日本語入力)を英数(半角英数)モードにしてから操作すること**。日本語入力モードのままだと `Ctrl+B` 等のプレフィックス操作にキーが届かないことが実機で確認されている(2026-07-25)。文字入力に戻すときだけ日本語モードに切り替える。
- `Ctrl+B` を2回連続で押すと(tmux 互換仕様により)2回目はリテラルの `Ctrl+B` としてペインへ送られ、プレフィックスは不武装のままになる。狙ったコマンドキーが反応しないときは、まず1回だけ押せているか確認する。
- `focus-sidebar`(`Ctrl+B` → `Shift+S`)はトグル: サイドバーにフォーカス中に同じ操作をするとペインへフォーカスが戻る。

## 貼り付け(paste)

Windows 版 crossterm(0.29)は `Event::Paste` を生成しない構造的制約があり(Unix 版のみブラケットペースト・エスケープを解釈する実装)、素のままだと `/copy` などでコピーした複数行テキストを貼り付けたとき、1文字ずつの `Event::Key` として届いてしまい、含まれる改行のたびに Enter が押されたのと同じ扱いになって途中送信されていた。2026-07-25、これを緩和する回避策を実装(`app.rs` の `read_input_batch`/`pasteable_char`/`finish_paste_burst`): 通常文字キーが4ミリ秒以内に連続して届いたときだけ疑似的なペースト(`Event::Paste`)としてまとめ、既存のブラケットペースト処理(`paste`/`paste_sidebar`)にそのまま渡す。人間の通常のタイピング間隔(数十ミリ秒以上)はこの窓に収まらないため、普段のタイピングの挙動・レイテンシは変わらない想定。**実機確認pass(2026-07-25)**: 15行・382文字(日英混在+Markdown記号)のクリップボードを`micro`エディタに貼り付け、欠落・文字化けなく最終行まで正しく入ることを確認。貼り付け前後のタイピングにもラグなし。なお、PowerShellのシェルペインに直接貼り付けた場合は改行のたびに行が逐次実行される(1行ずつ別々のプロンプトで実行される)が、これはPowerShell/PSReadLine側がブラケットペーストモードを有効化していないために起きる現象であり、cmux側の挙動としては正常(テキスト自体は各行とも欠落・文字化けなく届く)。

> **訂正(2026-08-08、Phase 7)**: 上記のバースト束ね機構は、当時実際には機能していなかった。
> Windows の crossterm は1回のキー入力(貼り付けで注入された文字も含む)ごとに `Press`/`Release`
> の2イベントを出すが、`read_input_batch` は `Press` 以外を「バーストの終端」とみなしていたため、
> 貼り付け中の最初の1文字の `Release` で即座にバーストが打ち切られ、実際には1文字ずつ分断されたまま
> だった。上記の「実機確認pass」はテキストエディタ(`micro`)への貼り付けだったため気づかれなかった
> ——エディタは Enter が個別キーで届いても単に改行を挿入するだけで実害が出ないが、シェルや
> Claude Code のプロンプトのような readline 系の入力では、個別に届いた Enter が「その時点までの
> 入力を送信する」操作として解釈されるため、貼り付けが途中で送信されてしまっていた。`0011` で
> `Release` イベントをバーストの終端とせず無視するよう修正し、cmux ペイン内のシェル(Claude Code の
> `/copy` 経由を含む)への貼り付けで途中送信されないことを実機確認済み。

## タブ(tab)

| 操作 | prefix 経由 | Alt モードレス |
|---|---|---|
| 新規タブ (new-tab) | `Ctrl+B` → `t` | `Alt+t` |
| 新規ブラウザタブ (new-browser-tab) | `Ctrl+B` → `Shift+b`(`B`) | — |
| 次のタブ (next-tab) | `Ctrl+B` → `Tab` | — |
| 前のタブ (prev-tab) | `Ctrl+B` → `Shift+Tab` | — |
| タブを閉じる (close-tab) | `Ctrl+B` → `Shift+x`(`X`) | `Alt+x` |

タブがペイン幅に入りきらないとき、タブバーは自動で2段表示に切り替わる(実機確認済み。設定
`tabs.max_rows`、既定 `2`。`1` にすると従来の1段+スクロールに戻る)。2段でも入りきらない分は
既存の `‹`/`›` スクロールを1段目左端/2段目右端に表示して対応する。タブのドラッグ&ドロップも
2段レイアウトに対応済み(ポインタの行で対象行を決め、行内の左右位置で挿入先を判定)。

sidebar_files から `Enter`/ダブルクリックで開いたファイルのタブには、番号ではなくファイル名が
表示される(拡張子込み)。ラベルの文字数上限は設定 `tabs.max_width`(既定 `24`。値は4〜200に
自動clamp)で調整可能(超過分は `…` で切り詰め)。同名ファイルを複数開いても自動では区別され
ない(必要なら手動でタブ名変更)。

`Alt+x` は `close-tab` にバインドされているが、そのペインのタブが1つしかない場合は、タブが閉じた結果ペイン自体も自動で消える(`close-tab`→タブが最後の1つならペインごと畳み込むカスケードが既定動作)。したがって実質的に「タブが複数あるときはそのタブだけ閉じる、1つしかないときはペインごと閉じる」という挙動になる。

ペイン間の境界線はマウスでクリックしたままドラッグしても幅を変更できる(実機確認済み)。GUIエディタと異なりカーソル形状は↔に変わらない(ターミナル側の制約でアプリからは変更不可)が、ドラッグ自体は機能する。

### セッションビュー(sessions)

`toggle-sidebar-view`で切り替えられる3つ目のビュー。全ワークスペース・全スクリーン・全ペインの全タブ(shell/エディタ/ブラウザタブ)をフラットな一覧として表示する。今どの画面にいても、バックグラウンドで動いているタブを見つけて直接フォーカスできる。

- 一覧の各行はタブのタイトル(OSCタイトル、無ければ `shell`)と、それが属するワークスペース/スクリーン名をサブタイトルとして表示。
- サイドバーにフォーカスがある状態で `↑`/`↓`/`j`/`k`/`Home`/`End`/`PageUp`/`PageDown` で選択移動、`Enter`または行のクリックで選択したタブへジャンプ(必要ならワークスペース・スクリーンの切り替えも自動で行う)。
- 制約: cmux-tui はタブのOSCタイトルとcwd/PIDまでしか知らない。「Claude Codeのサブエージェントが何をしているか」のような意味情報は表示できない(タイトルにその情報が含まれていれば見える、という間接的な形にとどまる)。

## ファイルサイドバー内のキー(sidebar_files)

サイドバーにフォーカスがあるとき(`Ctrl+B` → `Shift+s` でフォーカス)に有効。prefix は不要。
プレーンな文字キーのみ作用し、Ctrl/Alt 併用は基本無効(例外は `Ctrl+j` / `Ctrl+k`)。

| キー | 動作 |
|---|---|
| `↑` / `Ctrl+k` | 選択を1つ上へ |
| `↓` / `Ctrl+j` | 選択を1つ下へ |
| `→` | 選択中のディレクトリをその場で展開(エクスプローラー風。複数フォルダを同時に展開したままにできる) |
| `Enter` | 選択を開く。ディレクトリ=展開、ファイル=`$EDITOR` で右の新規ペインに開く |
| `←` / `h` | 選択が展開済みディレクトリなら折りたたみ。そうでなければ選択を親ディレクトリの行へ移動 |
| `.` | 隠しファイルの表示トグル(展開中の全ディレクトリに再適用) |
| `/` | フィルタ(絞り込み)モード開始 |
| `~` | 表示ルートを再設定(reroot。展開状態はリセットされる) |
| `c` | 選択ディレクトリへの `cd` をフォーカスペインへ送る |
| `o` | 選択した `.html` / `.md` を右の新規ペインでブラウザタブとして開く(それ以外は「.html/.md のみ」メッセージ) |

### ファイルサイドバー内のマウス操作

| 操作 | 動作 |
|---|---|
| 行のクリック | その行を選択 |
| ディレクトリ行の `▸`/`▾` マーカーをクリック | 展開/折りたたみ(選択もその行に移動)。マーカー以外の部分をクリックした場合は選択のみで展開はしない |
| ファイル行のダブルクリック(400ms以内に同じ行を2回クリック) | `Enter` と同じ動作でファイルを開く |
| マウスホイール | 選択を上下にスクロール(サイドバーが Files ビューのときのみ有効。Workspaces ビューと同じ挙動) |

### 補足(実装挙動)

- サイドバーは1ディレクトリだけのフラット一覧ではなく、展開済みディレクトリをツリー状にその場へ差し込んで表示する(`▸`=折りたたみ、`▾`=展開済み)。ルート自体(表示上部のパス)はフォーカスペインの cwd に自動追従するが、展開/折りたたみ操作を一度でも行うとその追従は止まる(`~` で再度 reroot するまで固定)。
- `Enter`/`→`/ダブルクリックでファイルを開くと `$EDITOR` を右側の新規ペインで起動する(`app.rs` の `FileCommand::OpenEditor` → `Mux::split_with_command`)。既存ペインの内容を上書きしない。
  `$EDITOR` 未設定/空のときは `vi` にフォールバックするため、**Windows ではランチャで `EDITOR=micro` を設定する**(spec.md D5/D7)。
- **`Enter` は常にファイルをテキストエディタで開く**(HTML ファイルであってもソースコードが表示される。ファイル内容をアプリ内表示・レンダリングする機能は無い、という元仕様どおりの挙動)。HTML/MD をレンダリングしてプレビューしたい場合は `o` を使う。
- `o` は `file://` URL を組み立て、右側の新規ペインでブラウザタブとして開く(`FileCommand::OpenBrowser` → `file_url()` → `Mux::split_with_browser`)。既定では headful Chrome の実ウィンドウに表示されるが、`%APPDATA%\cmux\cmux-tui.json` に `{"browser": {"sixel": true}}` を設定すると、Windows Terminal(Sixel対応版、1.24系で確認済み)上で TUI ペイン内に直接プレビューを描画する(6x6x6色量子化・ディザリングなしの簡易レンダリング)。既定は無効(opt-in)。
