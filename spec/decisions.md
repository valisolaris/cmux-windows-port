# 決定ログ — cmux Windows 対応仕様

書式: ラウンドごとに 質問/回答/採用理由/捨てた選択肢 を追記する。仕様の本文は `spec.md` が正。

## Round 0(2026-07-23)— 現物調査(質問なし)

Explore(sonnet)で `my-cmux\cmux` を調査。ROADMAP.md・メモリの既存記述と**食い違いは無し**。ただし既存記述より強い/新しい事実が2点:

1. **`sidebar_files` の存在**: cmux-tui にファイルサイドバーが実装済み(フォルダ閲覧・フィルタ・Enter→`$EDITOR` を新規 PTY タブで起動・`o`→HTML/MD を browser タブで開く)。「コード閲覧機能は無い」は「ファイル内容の表示機能は無い」が正確で、フォルダ閲覧+エディタ起動の土台は既にある。要望②の工数前提が下がる。
2. **`probe_kitty_graphics()` が Unix 専用実装**: Windows では端末の kitty graphics 対応有無に関わらず常に「非対応」判定。「Windows Terminal では画像が出ない」ではなく「**コード修正なしでは、どの端末でも in-TUI 画像は出ない**」が正確。WezTerm 採用だけでは要望③の in-TUI 表示は成立しない。

補足事実: browser pane は既定 headful(実ウィンドウが開く)・既存 Chrome/Edge を CDP 起動・ダウンロード機構なし。frontends/web は browser surface 未実装+Node 未導入。`$EDITOR` 未設定時のフォールバック `vi` は Windows に存在しないため、エディタの選定・設定が必要。

## Round 1(2026-07-23)— 主要4論点(いずれも推奨案をユーザーが採用)

### Q1 実行形態 → **ネイティブのみで go(D1)**
- 理由: ネイティブビルドは 2026-07-23 に検証済み(exit 0・起動確認)。管理者権限・再起動不要で最短経路。
- 捨てた選択肢: 「WSL2 将来枠」— 未検証の選択肢を spec に残すと保守対象が増えるだけで、必要時に別ランで検討すれば足りる。「WSL2 も今回検証」— 導入にユーザー作業(管理者権限+再起動)が必要でフェーズが増える割に、ネイティブ成功済みの今は得るものが薄い。

### Q2 コード閲覧 → **sidebar_files + CLI エディタ(D2)**
- 理由: Round 0 で判明した既存機能(sidebar_files)をそのまま使えば、追加実装ゼロで「フォルダ閲覧+ファイルを開く」が成立。TUI 内で完結し cmux 的体験を壊さない。工数最小。
- 捨てた選択肢: 「VS Code 連携」— TUI の外に出る上、`code` が即 return する挙動への手当(タブ即終了問題)が必要。「ビューア pane 自作」— SurfaceKind 追加+ハイライト実装は工数大で、フォーク保守負担が恒久的に増える。閲覧要件は CLI エディタで満たせる。

### Q3 HTML プレビュー → **headful Chrome 実ウィンドウ(D3)**
- 理由: browser pane の既定動作そのままで「実画面プレビュー」の要望を直接満たす。工数は動作検証のみ。
- 捨てた選択肢: 「kitty 移植を stretch」— stretch 枠でも WezTerm 導入+probe の Windows 実装が付いてきて、スコープが膨らむ。in-TUI サムネイルは要望に含まれない。「kitty 移植を必須」— probe_kitty_graphics が Unix 専用実装のため工数中〜大+成否不確実。要望③の本質(実画面で見たい)には headful の方がむしろ適合。

### Q4 ターミナルホスト → **Windows Terminal(D4)**
- 理由: Windows 11 標準で導入済み。D3(headful 方式)により端末の graphics 対応が不要になったため、機能面の不足なし。
- 捨てた選択肢: 「WezTerm」「WT 主+WezTerm 実験用」— kitty graphics 経路を捨てた(D3)ため導入理由が消滅。

- 派生した新未決事項: #9「build.rs 問題の upstream 報告をスコープに含めるか」(ローカルパッチを恒久化する前提が D1 で固まったため)。

## Round 2(2026-07-23)— 残論点4問(いずれも推奨案をユーザーが採用)

### Q5 エディタ → **micro(D5)**
- 理由: メモ帳感覚のキー操作(Ctrl+S/Ctrl+Q)で学習コストほぼゼロ。ハイライト内蔵で「閲覧+軽い編集」という要望②の実態に十分。winget で管理者権限なし導入可。
- 捨てた選択肢: 「helix」— 閲覧体験は最上位だがモーダル操作の学習コストがあり、要望②に対して過剰。「neovim」— vim 習熟が前提で、素の状態では体験が薄く設定工数が発生。

### Q6 フォーク保守 → **一点改造・コミット固定(D6)**
- 理由: 再現性最優先。windows-port ブランチにパッチをコミットすれば checkout/stash で失われるリスクが消え、ビルド再現手順が git だけで完結する。保守負担最小。
- 捨てた選択肢: 「upstream 追従」— 追従のたびにビルド再検証の手間と破損リスク。個人利用の一点ポートに定期 rebase の便益が見合わない。「非コミット運用」— 作業ツリー変更は喪失リスクがあり再現性の観点で論外。

### Q7 配布/起動 → **release ビルド+ランチャ+WT プロファイル(D7)**
- 理由: 日常使いの完成形まで作り切る。環境変数(EDITOR 等)はランチャ内設定に閉じ込め、システム環境を汚さない。
- 捨てた選択肢: 「ランチャのみ」— WT プロファイル登録は一度きりの小工数で日常の起動摩擦を大きく下げるため、省く理由が弱い。「debug exe 直接」— release 未検証のまま日常使いに入ると性能・サイズで損し、検証機会も失う。

### Q8 upstream 報告 → **任意タスクとして記載(D8)**
- 理由: 「upstream 報告に値する」というスパイクの知見を無駄にせず、かつ外部公開アクションを完了条件にしない(進行をブロックしない)。下書きまで作れば起票の判断コストが最小になる。
- 捨てた選択肢: 「スコープ内(起票を完了条件)」— 外部アクションが必須化し、プロジェクトの完了が外部要因に依存する。「やらない」— 知見の放棄。下書き作成の工数は小さい。

### D9 フェーズ分割(司令塔設計 — ユーザー質問なしで決定)
- 内容: Phase 2a(フォーク固定化+release ビルド)→ 2b(TUI 対話動作=要望①)→ 2c(要望②③)→ 2d(配布導線)→ 3(一気通貫の受け入れ検証)。
- 理由: 決定 D1〜D8 から機械的に導出できる依存関係(ビルドが通らなければ対話検証は不可能、対話が成立しなければ②③の検証は無意味)であり、ユーザーに聞く価値のある分岐がない。未検証事項6点(spec.md「実装時の検証ポイント」)を各フェーズの完了条件に割り付けた。凍結承認時にフェーズ分割も含めて承認を取る。

## Round 3(2026-07-23)— 凍結ゲートでのユーザー追加要望

### Q9 凍結承認(1回目)→ **条件付き: 「最後に忘れずに README とマニュアルを作って欲しい。マニュアルは項目に遷移しやすいように HTML ベースで」→ D10 として取り込み**
- 決定(D10): README = `my-cmux\README.md`、マニュアル = `my-cmux\docs\manual.html`(単一 HTML、目次アンカーで項目遷移)。作成タイミングは Phase 3。
- 配置・タイミングは司令塔判断: 「最後に」というユーザー指定に加え、マニュアルは実機検証済みの挙動(キー操作・起動手順)を書くべきもので、Phase 2b〜2d の検証結果が揃う Phase 3 が唯一合理的な位置。場所は my-cmux 直下(README)+ docs\(マニュアル)とし、参照用 zip の cmux-main やフォーク内部(cmux\)には置かない(フォークは一点改造 D6 のため upstream ファイルとの衝突を避ける)。
- 捨てた選択肢: 「マニュアルを Markdown で」— ユーザーが HTML ベースを明示指定。「フェーズ途中で書き始める」— 未検証の想定が混入し、検証後に書き直しの二度手間になる。
