## Round 1(2026-07-26)— 4問とも推奨案で確定

### Q1. ファイル名表示の実現方式 → split_with_command チェーンに name パラメータ追加
- 回答: mux.rs:3272-3283 / session/mod.rs:714-730 / app.rs:1847-1860 の3層に `name: Option<String>` を通し、生成直後に `Surface::set_name`。
- 採用理由: `RunCommandOptions.name`(mux.rs:2451-2453, 2544-2546)という既存の同型前例があり設計リスクが低い。オープン時点で絶対パスが確定しているため決定的で、エディタの挙動に依存しない。
- 受け入れたトレードオフ: シグネチャ変更が3層に及ぶ(機械的な変更)。
- 捨てた選択肢: SurfaceCreated 完了ハンドラでの後付け紐付け(対応付け状態の管理が必要で連続オープン時の取り違えリスク)/show_titles + OSC タイトル依存(エディタ依存で未検証・グローバル副作用あり)。

### Q2. 有効化の形 → 常時ON(設定なし)
- 採用理由: 番号表示より情報が増えるだけで害がなく、個別に戻すのは既存の RenameTab(config.rs:829)で可能。設定項目の増殖を避ける最小実装。
- 捨てた選択肢: 新設定・既定ON(設定が1個増えるだけの価値がない)/新設定・既定OFF(自分の要望機能を毎回有効化することになる)。

### Q3. 名前の中身 → ファイル名のみ(拡張子込み)
- 回答: `path.file_name()` をそのまま使う。同名ファイルの複数オープンは区別しない(必要時は RenameTab で手動区別)。
- 採用理由: 要望「HTMLのヘッダータブのように」に合致し、実装が確定的で最小。
- 捨てた選択肢: 親ディレクトリ付き(常にラベルが長くなり上限を圧迫)/同名時のみ親付与(既存タブの書き換え走査が必要で複雑さが要望に見合わない)。
- 派生: 親ディレクトリ案の消滅により「区切り文字(\\ か /)」の論点も消滅。

### Q4. 16文字上限の緩和方法 → 設定値化(既定24)
- 回答: `Tabs`(config.rs:642-666)に上限設定(仮称 `max_width`、既定 24)を新設し、`truncate(t, 16)`(pane.rs:240-252)の 16 を置換。
- 採用理由: 既定24で「いまより少し広く」という要望に合致し、好みに応じて調整可能。`min_width`(パディング)とは役割が別なので独立させ、既存設定の意味を変えない。
- 捨てた選択肢: 固定値24へ引き上げ(調整余地なし)/min_width へ統合(既存設定の意味が変わり互換性が壊れる)。
- 注: 項目名の最終確定(max_rows/min_width との命名整合)は Round 2 で行う。

## Round 2(2026-07-26)— 4問とも推奨案で確定

### Q1. パッチ分割と 0007 との適用順 → 独立パッチ 0008、0007 の後に積む
- 採用理由: パッチ集は連番の直列スタック。0007 を先に実装すれば、発行済みの 0007 handoff.md が参照する行番号の正確性が保たれる。0007 だけ適用した状態(番号タブのまま2段化)も成立し、機能的依存はない。
- 捨てた選択肢: 0008 を先に実装(0007 handoff.md の行番号がずれ改訂が必要)/0007 へ同梱(別機能のスコープ混在、レビュー・巻き戻し単位が粗くなる)。

### Q2. 設定項目の命名 → `max_width` のまま(既定24)
- 採用理由: 既存 `min_width`(ラベル最小幅・パディング)との min/max 対が既存ユーザーに最も自然。誤読は doc コメントで防ぐ: `max_width`「1タブのラベルの最大文字数」、`min_width`「ラベルの最小幅(パディング)」、`max_rows`「タブバーの最大段数」と3項目の対象を明記して揃える。
- 捨てた選択肢: `max_label_width` へ改名(min_width と非対称になり、かえって min_width の対象が曖昧に見える)/`tabs.label` 節の新設(既存 min_width の移設か重複が必要で設定互換性の問題を自ら作る)。

### Q3. 全角文字の扱い → 現状踏襲(文字数ベース)
- 採用理由: 表示幅(East Asian Width)対応は truncate だけでなくパディング(min_width も文字数ベース)や widths/fits の座標計算全体の一貫改修が必要で、本件の範囲を大きく超える。文字数ベース起因の座標ズレは RenameTab 日本語名で今も存在する既存制約で、本件が新規に持ち込む問題ではない。実害が出たら別件(表示幅対応)として起票。
- 捨てた選択肢: 表示幅ベースへ変更(unicode-width 依存追加+ラベル周り全体の改修で規模が数倍)/保守的な上限値(半角ファイル名の恩恵を削るだけ)。

### Q4. テスト方針 → ユニット2点+実機確認
- 回答: (1) tab_label() の name 最優先(config.rs:2295-2312 の隣に追加)、(2) 切り詰めが max_width 設定値に従う(既定24・境界値)。3層の name 伝搬は実機確認で担保。
- 採用理由: 機械的なシグネチャ変更に結合テストハーネスを新設するのは機能規模に対し過大。カバレッジゼロ地帯に最低限のユニットを足しつつ、結合は実機目視。
- 捨てた選択肢: 結合テスト追加(非同期パイプラインのハーネス整備が過大)/テスト無し(退行を検知できない)。
